# Elite Vent Room: Material-aware physics destruction with cinematic HUD

Complete overhaul of the Vent Room feature from a basic tap-and-toss destruction demo into a cinematic rage-room experience built on material-classified physics, programmatic particle systems, progressive environmental storytelling, and a multi-layered SwiftUI HUD synchronized with the SceneKit engine. The architecture centers on `RageRoomSceneManager` as the physics/audio/haptic brain, publishing state (combo count, destruction level, camera shake offsets, slow-motion flag, screen flash) to a reactive SwiftUI overlay that independently manages its own animation timelines. Supporting views (recording, playback, paper burn, release) received parallel premium-animation treatments.

Watch for: Timer and particle emitter lifecycle management may leak if the view is dismissed mid-destruction (confirmed). Damage numbers mutate array state inside `withAnimation` closures in a pattern that can silently drop updates when two hits land within the same animation frame (likely). The dual combo timeout (1.5s in engine vs 2.0s in HUD) creates a brief desync window where the banner shows a dead combo (confirmed).

**Verdict**: APPROVED

## High-level view

The core design splits state ownership cleanly: `RageRoomSceneManager` owns everything 3D and publishes a small set of `@Published` values that the SwiftUI `DestructionRoomView` observes. The cost is duplication of the combo timer: the scene manager resets after 1.5s while the view hides text after 2.0s, creating a 0.5s window where the HUD shows a combo the engine no longer recognizes.

The material system (`ObjectMaterial` enum with weight, fragility, color, sound IDs) drives every interaction pathway: targeting priority, force scaling, particle selection, audio layering, haptic pattern, and debris geometry. The 7 particle emitters are all fully programmatic `SCNParticleSystem` instances with property controllers and custom `UIGraphicsImageRenderer`-generated textures — zero asset dependencies. Those textures are regenerated on every emit call rather than cached, creating unnecessary allocations during high-combo bursts.

Progressive room deterioration runs in 4 phases keyed to `destructionLevel` and mutates lighting, spawns autonomous ceiling debris, activates a sparking pipe, and culminates in dropping the hanging light fixture as a dynamic body. The randomized trigger cadence keeps each session visually distinct.

The cinematic intro sequences 6 `DispatchQueue.main.asyncAfter` stages over 3.2 seconds with no cancellation path. If the user navigates away mid-intro, pending dispatches still fire against stale state — not a crash (value-type `@State` captures), but haptics and animations can fire after the user has left.

`DestructionRoomView.startEmberSystem()` creates a repeating timer that is never stored or invalidated, so navigating away mid-session leaks the timer and keeps the scene manager alive indefinitely.

<summary>Issues (5)</summary>

1. **Ember/particle timer leak on early dismissal** — `DestructionRoomView.startEmberSystem()` creates a repeating `Timer.scheduledTimer` that is never stored or invalidated. If the view is dismissed while the timer is alive, it continues firing. Store the timer in `@State` and invalidate in `onDisappear`.
2. **Dual combo timeout desync** — `RageRoomSceneManager` resets combo after 1.5s idle; `DestructionRoomView` hides combo text after 2.0s idle. This creates a 0.5s window where the HUD shows a combo the engine no longer recognizes. Unify the timeout or have the HUD read `sceneManager.comboCount == 0` as the authoritative signal.
3. **Damage number array mutation under animation** — `spawnDamageNumber` appends to `damageNumbers` then mutates `opacity` inside `withAnimation`. If two hits overlap, the `firstIndex(where:)` lookup may find a stale entry or miss. Consider using a dedicated `AnimatableData` model or moving the fade to a `TimelineView`.
4. **Cinematic intro dispatches fire after dismissal** — The 6-stage `DispatchQueue.main.asyncAfter` sequence in `playCinematicIntro()` has no cancellation path. If the user taps "back" during the 3.2s intro, haptics and state mutations fire into a deallocated view hierarchy. Use `Task`/`withCheckedContinuation` or store a cancellation flag.
5. **Particle image regeneration on every emit** — `createCircleImage`, `createDiamondImage`, `createSplinterImage` are called fresh each time a particle system is created. For high-combo scenarios with multiple emitters per second, cache these images as `lazy` properties.

## Material-aware targeting and force pipeline

Target selection uses a camera-forward dot-product scoring system within a ~78-degree cone (`alignment > 0.2`), weighted by `alignment * 2.0 - distance * 0.3`. This strongly favors objects the camera is pointed at, creating the illusion of aimed hits without a raycast. Effective force flows through:

```
toolForceMultiplier (2.0-4.5)
  * comboForceMultiplier (1.0-2.5 at 15+ combo)
  / materialResistance (weight / 10.0, clamped to 0.5 minimum)
= effectiveForce
```

`effectiveForce` then drives: physics impulse magnitude, particle burst count, camera shake intensity, slow-motion threshold, and destruction level increment.

One subtlety: `ObjectMaterial.concrete` has weight 20.0 (resistance 2.0), meaning a fist hit (multiplier 2.0, no combo) yields `effectiveForce = 1.0`. Concrete is nearly indestructible by fists alone — intentionally correct, but means cinder blocks require the sledgehammer.

## Timer and emitter lifecycle (confirmed leak path)

```swift
Timer.scheduledTimer(withTimeInterval: 0.4, repeats: true) { _ in
    guard sceneManager.destructionLevel > 0.1 else { return }
    // ... spawns embers
}
```

This timer is never assigned to `@State` and never invalidated. The closure captures `sceneManager` (a `@StateObject`), keeping the manager alive and the timer firing indefinitely after navigation away. The same pattern appears in `startLeafParticles()`, though that function is defined but never called (dead code).

In `RageRoomSceneManager`, `dripTimer`, `comboTimer`, `slowMotionTimer`, and `slowMotionRampTimer` are stored but never invalidated in `deinit`. However, all timer closures consistently use `[weak self]`, so once the `@StateObject` releases, timers can't prevent deallocation. The view-layer ember timer does not use weak references and does not store the timer — that's the confirmed leak.

## Combo state duplication

The engine resets combo at 1.5s via timer, publishing `comboCount = 0`. The view observes this via `onChange(of: sceneManager.comboCount)` and hides the combo when it hits 0. But separately, the view's own 2.0s `DispatchQueue` also tries to hide the combo. During the 0.5s gap, the engine says "no combo" while the banner is still visible. Cosmetic only — the combo's mechanical effects (force multiplier, slow-mo eligibility) are governed solely by the engine's count.

## Performance: particle image allocation

`emitSparks` calls `createCircleImage(size: 8, color: .white)` on every invocation. At GODLIKE combo rates (15+ hits within 1.2s windows), a player tapping rapidly could trigger 2-3 emitters per second, each generating a fresh `UIImage`. These are tiny (8x8 px) but caching as lazy properties would eliminate the allocation entirely. The hard caps on debris (80), spray (200), and cracks (40) effectively bound the scene at ~375 active nodes worst-case.

## Slow-motion edge case

Slow-motion activates (sledgehammer at 3+ combo, bat at 5+ combo, any tool at 10+ combo), sets physics speed to 0.3, holds 0.8s, ramps back over 0.3s. Re-triggering is prevented by checking `isSlowMotion`. But since `isSlowMotion` remains true during the ramp-up phase too, rapid sledgehammer combos get at most one slow-mo per burst. This prevents stacking but also means a 15-hit GODLIKE sledgehammer streak only gets a single slow-mo at hit 3 — arguably underselling the moment.

## Gesture recognition delay

The gesture stack combines double-tap (rapid fire), single-tap (hit), drag (swipe/throw), and long-press (charged attack). Double-tap takes priority, introducing a ~200ms delay on single-tap recognition. For a destruction game this likely adds satisfying weight, but if users report "lag," this is the cause.

## DestructionRoomView hit-testing depth

11 Z-ordered layers with `allowsHitTesting(false)` means every touch walks through ~8 non-interactive layers before reaching the SceneKit view. SwiftUI short-circuits this internally via layer flags, but the stack is deep enough that adding more overlays could eventually show in Instruments trace under `UIEvent` delivery.
